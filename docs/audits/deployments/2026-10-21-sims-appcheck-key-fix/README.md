# Production deployment: SIMS sign-in restored (App Check key missing from live build)

On October 21, 2026 staff could not sign in to https://bnhs-sims.web.app. The sign-in screen showed "This browser didn't pass the site's security check". The user asked for the release tree to be rebuilt and republished. Only `hosting:sims` was published.

## What was wrong

- About 21:05 UTC (05:05 Manila) SIMS hosting was published again, about 12 minutes after the verified Subject Teacher retirement release (`../2026-10-20-retire-subject-teacher/`, main script `index-D9WRJGvm.js`). That publish has no deployment record.
- It was not the release tree. A plain build of `master` without `VITE_RECAPTCHA_SITE_KEY` reproduces it exactly: main script `index-CQxXV8g7.js`, `ui-B7AP3ghp.js`, `index-BQ8ovFRo.css`. 40 of the 59 recorded release files differed.
- `src/firebase.js` only starts App Check `if (import.meta.env.VITE_RECAPTCHA_SITE_KEY)`. With the key empty the build dropped `initializeAppCheck` entirely, and the live bundle contained no `6L…` site key.
- Firebase Authentication on `bnhs-sims` enforces App Check. A tokenless sign-in request to the Auth API returned `401 Firebase App Check token is invalid.`, which `src/lib/authErrors.js` shows as the security-check message. Every sign-in was refused before the password was checked.
- The published build was `master`, which carries the held coordinator rollout. No staff member could sign in while it was live, so the UI could not have written through it.

## Change

Rebuilt `docs/releases/2026-10-20-retire-subject-teacher/prepare.mjs` into `.superpowers/releases/retire/release` (via a temporary `subst R:`), linked the main checkout's `node_modules`, and built `sims` with the main checkout's `.env` loaded for the build process only (`set -a; . <main checkout>/.env; set +a; npm run build`).

Checks before publishing:
- Main script `index-D9WRJGvm.js`, as recorded for the release.
- 59 of 59 files matched `../2026-10-20-retire-subject-teacher/sims-hosting-verification.json` by SHA-256.
- The 40-character site key is in the main script, passed to `ReCaptchaEnterpriseProvider` and `initializeAppCheck`.
- Live `index.html` was rechecked immediately before publishing (still the `master` build).

Publish command (config regenerated by the preparer, SIMS target only):

```
NODE_OPTIONS=--dns-result-order=ipv4first npx firebase deploy --project bnhs-sims --config firebase.retire-subject-teacher-release.json --only hosting:sims --non-interactive
```

See `hosting-sims-deploy.log`.

## Verification

- **Byte check:** all 59 files served by https://bnhs-sims.web.app match the deployed build by SHA-256 (`hosting-sims-verification.json`). Main script `/assets/index-D9WRJGvm.js`, `Last-Modified` 21:24:35 UTC.
- **App Check in a clean browser:** the page loaded reCAPTCHA Enterprise and `exchangeRecaptchaEnterpriseToken` answered 200. The broken build made neither request.
- **Not checked:** a real staff sign-in. It needs a real password, so the user confirmed it themself.

No functions, Firestore rules or indexes, App Check or Auth settings, school records, Parent App hosting or kiosk hosting were changed. Release tree tests were not rerun: the output is byte-identical to the build verified on October 20.

## Prevention

- Before any SIMS hosting publish, confirm the built main script contains the 40-character `6L…` site key. A build without it deploys cleanly and fails only at sign-in.
- Never publish a root or `master` build of SIMS while the coordinator rollout is held; use the release tree.

## Rollback

The release tree is the intended production state, so rolling back is not expected. The previous version (the `master` build, main script `index-CQxXV8g7.js`) cannot sign anyone in. To go back to the Subject Teacher release's earlier state, use the Hosting console and pick a version whose main script is `index-DIiDC7eb.js`, which predates the retirement release.
